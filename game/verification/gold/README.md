# G単位・端数の見直し

基準main: `72b13f28667390d0791aca44806ac5cce03898ed`（#95まで）。他のUI・ジョブ変更は取り込まない。正式データと本体JSを使い、実ユーザーの保存データは使わない。

## 変更

- 旧1Gを新10Gへ。正式CSVや既存数式は基準単位を保ち、GameData構築時に明示した金額項目だけを換算する。復活・装備店・強化など固定式は出力を換算する。
- 新たな単価・報酬の丸め幅は `max(10, 10^(floor(log10(金額))-2))`。1万G未満は10G、1万G台は100G、10万G台は1,000G、以降同様。大きい桁では元の計算値を直接丸め、二段階四捨五入を避ける。小額では旧計算のround/floor/ceilを10倍単位で維持。正の金額を0Gにしない。
- 数量×単価の合計、所持金、借入元本、預かり金の全額返還、既存契約額は再丸めしない。まとめ買いの端数差益や残高の目減りを防ぐ。金額合計に細かい桁が残ることは意図した例外。
- **融資上限のみ切り上げ**。会費は廃止済みだがguild_feeは上限計算の入力なので、ここは丸めず正確に10倍。旧最大合法借入が新上限を超えないことを全ランクで検証。
- 受注済み/保存済み掲示は元金額を正確に10倍し、特別依頼の期限加算も旧約定の丸めを維持。期限、保証金率、報告条件、ポイント・素材・AP/XPは変更しない。
- 任意の借入・返済入力は入力額をそのまま移動する。手入力の1G単位や古い返還記録・過去のお知らせを、新しい見積額の丸め対象にはしない。月末利息は従来の最低1旧G（10新G）刻みを維持する。

## 入出金監査

|流れ|対応・検証|
|---|---|
|初期財布|new_game.goldを正確に換算。新規gameにgoldVersion=1|
|掲示・受注・報告|通常/特別・保証金・期限加算・放棄・全額返還。旧board/quests/specialQuest/地域別旧掲示も換算|
|戦闘・探索|敵1体のG、ボス/エリート倍率、戦闘後G補正、宝箱、探索依頼のG。率と非G報酬はそのまま|
|出発・宿・神殿|遠征費、安い/良い宿、復活式、治療費。ジョブ素材奉納はG不要なので変更なし|
|店・売却|割引後の単価と実控除を一致。装備売値、数量購入、所持枠は従来通り|
|工房・投資|通常/専用制作、調合、強化、付与、施設投資、バックパック拡張。分解/振り直しは素材だけでG無料を維持|
|銀行|元本、上限、利息、任意額借入・部分返済。預金システムは現行に存在しない|
|旧機能の精算|ルーン枠返還と廃止連続依頼の未精算額/精算記録。返還済みフラグを保ち二重付与なし|
|闘技場等|直接のG入出金はなし。交換単位・XP/APは変えない|
|開発保存テスト|仮報酬10旧G→100新Gと表示を一致。通常の開発メニュー方針は変更しない|

### セーブ

保存キーは同じ。外側のSAVE_VERSIONを1→2へ更新し、旧クライアントが更新後セーブを旧単位で編集しないよう既存の新版本readOnly判定を使う。v1の中身は保持して読み、正式データ読込後にnormalizeGameで通貨を移す。game/run/入場前snapshotを個別のgoldVersionで一度だけ換算し、未知の非G項目は落とさない。goldLegacyContractで旧契約の約定を区別する。AP・職・装備・ID・学習記録・戦闘状態は変更しない。

追加指定ケース：v1遠征中の現在1,037G/借入111G、入場前1,000G/借入111G、獲得37Gを保存。読込→10,370/1,110、snapshot10,000/1,110、earned370へ換算。再読込で不変。全滅→10,000/1,110。80G部分返済→9,920/1,030。再正規化でも不変。`game/tests/gold.test.js` で検証。

古いタブを開きっぱなしにしたまま複数タブで保存する競合は既存の単一セーブ方式の制約で、今回新しい排他制御は導入していない。更新時は再読込が必要。過去のお知らせの文章は歴史記録として旧単位のまま残し、移行時にその旨を通知する。

## 計測

`measure.mjs` は正式CSV/JSONと実ゲームの遭遇・ドロップ・依頼受注/報告・店・売値・宿を利用。基準mainを別worktreeで読んだbefore、10倍/3桁、100倍/3桁、10倍/2桁を同じseedで比較。

- 64seed（112501+i×7919）、春、エリートなし。森→洞窟→採石場を3周、その後R02へ進んだスナップショットで砦→湿原を3周。各条件960遠征相当の**成功した経済経路**。各回ポーション2個、遠征費、安い宿を払い、拾った装備は全売却。該当地域の討伐依頼を受け、実際の出現敵IDの討伐数で報告する。
- R02入りで店の上位剣を1本実購入。対象地域の固有素材/報酬を初入場の前提にしない。1経路の購入はポーション30個＋剣1本、宿15回。
- 戦闘勝敗・問題数を再計測したものではない。クリア条件付きの現金推移で、ポーション2個消費は固定費シナリオ。全戦勝利、全装備売却という仮定のため貧窮リスクの上限評価には使えない。昇格試験・教材・SRS・死亡/治療・宝箱・ボス/特別依頼の報告を含む完全新規プレイでもない。省いた入出金は個別見積/回帰テストで扱う。
- 全ランクで店単価4,775件、専用制作・調合・付与・施設・鞄・融資上限288件（無料2件含む）を比較。正の額のゼロ化、新たな店買い→即売りの利益を検出する。

|候補|店価格の実質変化範囲|960時点の財布変化範囲|購入可能な武器数が違う時点|
|---|---:|---:|---:|
|10倍・3桁（採用）|−0.362%〜+0.444%|0%|0|
|100倍・3桁|−0.362%〜+0.444%|0%|0|
|10倍・2桁|−4.762%〜+4.167%|−0.260%〜+0.660%|355|

100倍は同じ購買力だが、初期所持金10万G・53G依頼5,300Gとなる。まず10倍で数字を大きくし、桁数の膨張を抑える。2桁案は購入可能数を変えるため不採用。

seed112501の15周後は3,484G→34,840G、R02上位剣は125G→1,250G、残高で買える本数27本で一致。最初の森1周は1,000→1,047G、新単位10,000→10,470G。結果JSONは全64seedの最終残高、サンプル全15周、全その他見積と差率、入力/エンジンのhashを収録。フル試行/店単価一覧はスクリプトで再生成できる。

## 再現コマンド

Node.js、Python3。本体JSで計測。基準worktreeは既存の差分を含まない隔離先を使う。

```sh
git worktree add --detach /tmp/english-quest-gold-base 72b13f28667390d0791aca44806ac5cce03898ed
GAME_ROOT=/tmp/english-quest-gold-base node game/verification/gold/measure.mjs /tmp/gold-before.json
node game/verification/gold/measure.mjs /tmp/gold-after.json
SCALE=100 node game/verification/gold/measure.mjs /tmp/gold-100.json
SCALE=10 DIGITS=2 node game/verification/gold/measure.mjs /tmp/gold-2digit.json
python game/verification/gold/summarize.py
npm --prefix game test
```

ブラウザはリポジトリルートをHTTP配信し、PlaywrightとChromiumを使う。実セーブとは別の新contextを毎回作る。

```sh
python -m http.server 8772 --bind 127.0.0.1
# 別ターミナル。必要ならNODE_PATH、CHROMIUM_PATHを環境に合わせる。
BASE_URL=http://127.0.0.1:8772 node game/verification/gold/browser-smoke.cjs
```

320/390pxで普段のギルド酒場から53旧Gの保存済み依頼を530Gとして報告し、道具屋で5個1,000Gの確認・キャンセル・確定、銀行で部分返済、再読込を実証。画像は/tmp/gold-board-320.pngと390.png。今回は実ブラウザで全施設・全ランクの手動操作、公開環境への反映、旧タブとの同時保存は未検証。

## テスト結果
